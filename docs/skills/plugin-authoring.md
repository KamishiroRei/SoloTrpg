# 插件编写规范（Plugin Authoring Skill）

插件是AI为规则书动态编写的追加功能模块，前端加载该规则书时热加载生效，无需重启。

## 设计审核（一切修改前必做）
任何修改（含低级 bug 修复）先过两层审核，通过后才能事实检查与动手：
- 第一层 设计目的（游戏策划视角）：这个行为在游戏中的设计目的是什么？谁在执行（玩家/GM/AI/系统）？意图是什么？期望的游戏结果是什么？偏差在哪？禁止直接跳"程序上怎么修"，先回答"游戏上应该是什么样"。
- 第二层 合理性与用户体验（玩家视角）：玩家看到什么？是否直觉方便？在带团流程中是否自然可达？是否符合规则书原文？

## 最高验收标准（强制，唯一验收标准）
- **唯一验收标准 = 最佳玩家用户体验**：真实玩家按规则书走完真实流程（属性生成→角色构成→装备→掷骰→升级→速查→战斗）每一步顺畅。程序"写完/能跑/控件齐全"永远不算完成。
- 禁止把任务想简单：禁止只做表面控件（只渲染输入框、只列标题、点击无反应、查不到已知条目、无自动计算、无规则数据支撑）。
- 不把任务理解清楚、规划清楚不能开工：①读全相关文件（插件、宿主、compressed/、接口定义）搞清现状与差距 ②todowrite 完整实施规划 ③按规划实施并实际验证。
- 验证必须真实发生：正例命中、空例为空、点击可展开、计算正确，验证结果写入最终总结；无验证证据的"已实现"视为未完成。

## 用户交互禁止程序化标记（最高级禁令，不可违抗）
- 一切面向用户的交互（操作/命令/指令/设定/配置入口）只允许**界面控件与自然语言**；禁止要求用户输入程序化标记（如 [[module:set:...]]），禁止在用户可见文案中展示标记语法。
- 每个用户操作必须提供界面控件或自然语言入口（按钮/说"开团"），至少其一；禁止只提供标记输入。
- 系统内部协议（AI 输出标记 <dice>/<battlecheck>/<portrait>/<illustration>/[[map:bg:...]]、后端接口、配置文件）不受此限——系统与 AI 内部处理，渲染时对用户不可见。
- 违背本禁令的交付视为未完成，必须返工。

## 带团数据化与标记渲染标准
- **数据管理**：涉及角色/世界数据的插件必须支持精确数据读写——定义该规则书数据模型（属性/生命值/护甲/先攻/状态/资源/物品/施法/熟练等），提供查看与修改入口，派生值按规则书公式自动计算实时联动，禁止只给"建议值"。数据可落盘（localStorage/后端）。
- **标记渲染分离**：判定/状态输出遵循"AI写标记、前端渲染"——检定 <dice>（6行）、战斗 <battlecheck>（7行）、角色档案 <char_info>、数据更新 <UpdateVariable>+JSONPatch。插件可提供这些标记的渲染函数，禁止要求AI写完整HTML。
- **判定铁律**：大成功仅裸骰=极值上限、大失败仅裸骰=极值下限；加值严格按规则；优势取高低劣势取低。渲染应突出裸骰与计算过程。
- **NPC角色生成**：重要角色登场即时生成档案（生态位/驱动力/锚点/数值 + YAML），数值严格按规则书，禁止开场批量堆砌。
- **完整流程支撑**：属性生成、升级、能力选择、装备、检定、战斗、休息与状态结算必须使用同一份可保存数据。
- 涉及带团体验设计时用 skill {"name":"gm-protocol"} 加载完整协议。

## 电子游戏级体验标准（最高规格）
- 每个规则系统=完整可玩的电子游戏模块：玩家按规则书走完整流程（创建→升级→战斗→速查→休息）每一步顺畅、数据精准、界面精美。
- 数据化精准：一切游戏数据（HP/AC/先攻/法术位/物品/状态/资源）结构化存储、可读可改、派生值公式自动计算实时联动；装备/效果影响数值（effectTags/effects），禁止纯文本摆数据。
- 角色卡等大型模块必含：①多角色管理（持久化+恢复+切换+删除+头像）②分页/标签导航 ③查看/编辑双模式 ④数据化字段（物品/法术结构化）⑤派生值自动计算链 ⑥效果系统 ⑦玩家驱动掷骰（可点击+日志高亮）⑧休息与资源 ⑨状态管理（HP/状态/死亡豁免/灵感）⑩AI接口（状态摘要供带团AI读取）。
- 视觉强制：视觉由规则模块按规则书与世界观设计，宿主不固定主题；对比度≥4.5:1，禁止#999/#aaa浅灰小字正文；语义色彩（红危险/绿成功/金资源/蓝信息）；标题衬线奇幻字体+正文现代无衬线；悬停反馈/tooltip/保存通知/展开收起动画。
- 验收：真实玩家走完真实流程每一步顺畅；"看不清/点不动/改不了/算不对/数据不落盘"五类缺陷为零。

## 界面组件库契约（强制；稳定 CSS 白名单）
宿主 style.css 提供统一组件类，插件界面一律复用宿主组件，禁止逐元素内联样式美化（视觉稳定、全插件一致、省 token）；宿主组件升级样式时全插件自动生效。
- **白名单**：按钮 .btn-small（可加 .accent）/ .cmd-btn（.primary/.gold/.danger）；条目化长条列表（参照 .adv-item/.module-item）；标签与浮动详情 window.TrpgTag（chip+bindTips）；卡片 .gm-card/.rules-card；弹层参照宿主 modal/.version-drawer；空状态 .rules-empty/.empty；聊天/骰子日志走宿主渲染。
- 输入/选择/搜索框用宿主既有样式，不单独定义新视觉。
- 确需新视觉组件（宿主确无同类）：插件内 <style> 定义**一次组件级类**（插件前缀命名，如 .myplugin-list），禁止逐元素内联。
- AI 输出聊天正文禁止输出 <style> 与内联美化（正文渲染交宿主正则与 CSS）。

### 美化决策流程（强制，标准化工作流）
写任何界面前按此顺序自主判断：
1. **默认不美化**：宿主组件能满足功能与可读性 → 直接用宿主类，零自定义样式。
2. **有需要才判断值不值**：宿主组件无法表达该规则书世界观或关键交互必须定制时，评估"体验提升 vs 样式定义+每轮上下文携带成本"；纯装饰性美化（渐变/花边/点缀）默认不做，除非规则书世界观确实要求。
3. **自定义也组件级**：通用视觉写成一次性组件级类（插件前缀命名），所有页面复用；样式量大的放在插件 index.js 顶部统一 <style> 一次、运行时注入一次。
4. **复用优先**：先在宿主 style.css 与已写插件中找同类组件，能复用绝不新写。
5. **收尾自查**：同一视觉是否只定义了一次？能否用宿主类替换？正文消息里有没有内联 style？

### 控件交付自查（强制，任何 UI 改动必查——含宿主与插件）
新增或修改任何界面控件（按钮/输入/下拉/弹窗/列表项），交付前按玩家视角逐项自查，缺一项即未完成：
1. **排版**：同类操作是否平行对齐在一行/一致网格，禁止散落多行堆叠、禁止注释式说明文字（说明放 title/悬浮提示，不放界面正文）；
2. **状态化**：该控件有无应禁用/应隐藏/应变化的状态（如默认项不可删除、无数据时置灰、权限不足时隐藏），且状态随数据变化实时联动（切换/加载/删除后立即刷新），禁止只做静态控件；
3. **反馈**：点击后有可见结果（数据变化/跳转/提示），失败有明确错误；
4. **流程**：真实玩家从入口走到结果每一步顺畅，无死路（按钮存在但点了没反应/被注释挡住/状态与数据矛盾）；
5. **极端情况**：空列表、默认值、权限不足、网络失败时控件仍合理。
历史教训：设置页"重置/删除冒险"曾以两行+注释式 hint 交付、默认冒险无禁用态、切换冒险不联动——属"机械化完成、未按玩家流程推演"，此类缺陷必须在本自查拦截。

## 标签系统底层（强制）
- 宿主提供全局标签系统 window.TrpgTag（app/js/tags.js），一切可枚举规则数据（特性/装备/法术/状态/效果/熟练/豁免/资源/学派/来源）必须以标签为基本展示单元，禁止平铺纯文本列表。插件内同源可用。
- **TrpgTag.chip({name, type, tone, source, extra, desc, detail, active, removable, dataAct, dataI})**：返回标签 HTML。type 决定色系（race/cls/bg/subclass/custom/feat/weapon/armor/shield/item/wondrous/tool/status/effect/spell/resource/save/skill/info/gold/neutral）；desc/detail 自动接入 hover 浮动详情。
- **TrpgTag.bindTips(container)**：绑定标签浮动详情事件委托（幂等，render 后调用一次）；**TrpgTag.dynamic(name, expr, ctx, opts)**：动态数值标签（@pb/@level/@strmod 等表达式实时求值）。
- 标签可携带 data-act/data-i 参与宿主事件委托；可移除标签（removable:true）点击 ✕ 触发宿主删除。
- **归类展示**：可动态添加且数量多的数据（装备/法术/物品）按规则自然类别分组（法术按学派+环位、装备按类别+武器细分），以横向列表条目管理（每行=标签+操作按钮），关键信息一眼可读，详情交标签浮动层。
- **武器攻击卡**：每件武器显示动态攻击修正（属性+熟练+魔法+效果累计）与伤害公式，可点击掷骰（暴击翻倍）。
- 宿主/规则插件统一使用该底层，禁止自造另一套标签样式。

## 界面定律
- 规则书功能必须放在规则书详情面板内：先一个**入口按钮**（标题+一句话说明），点击后展开/切换功能面板（可再次点击收起）。禁止常驻堆叠大块面板、禁止独立弹窗。
- 详情页是**一个容器**：插件入口填充/替换通用占位说明，不追加第二个独立模块；插件区与宿主详情页不得形成两个各自滚动的大模块。
- 详情插件占满可用宽度：不得给宿主插件容器设置 max-height 或独立 overflow-y（避免半空白+嵌套滚动区）。
- **固定尺寸框规范（强制）**：内容展示区块（角色设定、描述、列表、长文本等）一律使用固定尺寸比例的框（固定高度），内容超出用内部滚动（overflow-y:auto）；禁止动态高度/内容撑开式布局。
- **文本输出禁令（最高级）**：插件产出或 AI 写入的任何面向玩家文本（角色设定/描述/背景）只基于正面原本路径编写，禁止"没有X——原本是Y"式否定对比、禁止"（设定：...）"式自证元说明、禁止修正痕迹。

## 查询/速查质量（必须验证）
- 搜索插件必须查询完整规则资料：优先 /api/rules/index?system=<系统>&q=<关键词>&limit=<n> 或压缩表数据；禁止只取前150条索引本地过滤。
- 支持常见译名/别名/英文名（圣武士/帕拉丁/Paladin）；职业类还须搜索精确标题/路径关键词。
- 结果必须可操作：每行=名称|分类/来源路径|短摘要，全宽样式，点击用 api.openRuleFile 或 /api/rules/source 新窗口打开原文，再次点击可收起；列表头显示命中数；空结果统一提示（含别名建议）。
- 完成前实际验证：至少一个应命中的正例和一个应为空的反例，在总结中报告。只渲染输入框但查不到已知条目的插件不完整。
- 结果排序只是体验优化非阻塞项；优先修覆盖、可读性、交互与标准沉淀。
- 发现同类缺陷时，先补标准和系统频道提示词，再让目标AI按标准自迭代修复。

## 规则树整理归纳（Rule Tree）
- 规则内容整理为树状结构供速查导航（目录式、可折叠），写入 `Ruler/<系统>/compressed/rule_tree.json`：`{ system, tree: [ { name, source?, children: [...] } ] }`，叶子带 source 路径。
- 树按规则书实际结构构建（书→章节→小节→页面，语义归类合并）；总节点≤600。
- 解析阶段必做；已解析系统通过系统频道对话补完（不重跑解析、不移动 source/）。
- 速查/导航插件必须用 rule_tree.json 渲染树状导航，搜索作补充；禁止零散平铺。

## 选项内容自动化（Option-list Automation）
- 选项类内容（法术/装备/专长/能力等）必须自动来自规则书数据，禁止只有手动空输入框：优先读 compressed/ 预整理数据，缺失时从源文/索引运行时解析。
- 表格化结构化展示：按规则自然分组（法术按环位分组表格可勾选），自动列表可勾选/添加，同时保留手动输入/自定义入口（自动与手动并存）。
- 通用原则：任何规则的"可选内容"都按此自动化，不只法术。
- **扩展书自动捕获（强制）**：选项数据源=核心书+全部官方扩展书；构建/修改选项列表前先枚举 rule_index.json 确认所有扩展书条目、对照现有实现补齐；扩展条目缺失即未完成。第三方/UA 默认不自动收录，保留手动入口并总结说明。

## 规则内容文件化驱动（核心铁律）
> 法术/专长/装备等内容**不是搜索得到的，而是通过创建专门的文件得到的**。
- **内容文件化**：一切规则内容（法术/专长/装备/职业/子职业/背景/种族/怪物/物品/效果/资源）预先构建为专门的结构化数据文件（compressed/ 下 rule_*.json），插件直接加载文件驱动 UI。**禁止运行时搜索获取规则内容**（/api/rules/index?q= 仅作数据文件缺失时的最后兜底）；搜索式取数=未完成。
- **数据文件=游戏内容资产**：可编辑（官方默认+自定义入口）、可重建（_tools/ 脚本）、可校验（正例+空例+键完整性）；名称差异在加载层做索引与别名兼容（name/fullName 双索引、译名别名表），禁止把数据质量问题推给查找逻辑。
- **程序化计算**：一切数值由公式程序化推导（派生值/价格/负重/效果累计/环阶推导），数据文件只提供原始参数；禁止硬编码结果、禁止手填。玩家改动立即重算联动。
- **模块化结构**：单文件插件内 PART 分区；事件委托用 ACT 白名单路由表（禁止巨型 if 链）；状态单一事实源（候选与已分配分离）；槽位数组保持位置语义；数据加载统一编排（Promise+就绪标记+reconcile 重放）。
- **可编辑可热重载**：插件修改与数据文件修改都热加载生效；框架支持 AI 动态追加功能与动态修正内容。
- **举一反三**：方法论适用于所有内容域（法术/装备/专长/职业/物品/效果…），装备体系同样数据文件驱动+程序化联动（背包/AC/负重/购买扣除）。

## 角色卡游戏体验完整标准（通用）
> 只定义"必须从规则书提取并完整实现"，禁止把任何具体规则（DND 购点/生命骰等）写死为标准；参数一律来自该规则书解析产物。
- 完成标准=完整玩家游戏体验而非执行完毕任务；任何环节只做表面控件即未完成。
- 属性生成默认全做：规则书定义的全部标准生成模式（示例 DND：购点/骰点/标准数组/手动），缺任一=未完成；骰点自动出结果不展示过程、可重复掷；手动保留。
- 内容范围=官方内容：核心+官方扩展（示例 DND 含奇械师）；第三方默认不收录但留手动/自定义入口。
- 掷骰由玩家驱动（HP/属性提供掷骰按钮可重复掷、可手动输入）；禁止默认填最大/均值。
- 正式角色卡中属性=可直接修改的数字（生成模式只存在于创建流程）；派生值自动重算。
- 角色升级流程（Level-up）：按规则书提供完整流程（成长骰、等级派生值自动更新、能力/专长选择提示、法术类更新），数据落盘；规则书定义了升级就必做。
- 自动计算链完整（示例 DND：AC 护甲公式/先攻=敏修/DC=8+熟练+施法属性修正）；禁止只给建议值。
- 玩家视角验收：模拟真实玩家完整创建+升级一次并核对派生值。
- 技术核查：交付前检查所有独立窗口页面可滚动、缩放正常。

## 角色卡一体化（强制，取代"创建与修改分离"）
- 角色卡是**一个模块、三种模式**：创建=新建分步引导、查看=只读展示、编辑=完整分页表单。宿主右上角永远是"＋ 新建"；修改入口在角色卡页面内部。
- **数据驱动 TABS**：统一 TABS 定义（基础/种族/职业/背景/属性/技能/法术/背包/特性/笔记），三模式共用同一套分页定义与数据模型（token.data 单一结构），禁止两套页签/结构。
- **权限**：玩家名=玩家身份；角色 owner=创建者玩家名；修改权限=owner 或 GM，其他玩家只读；GM 可转交控制权（token_transfer）。地图位置移动放行所有玩家；数据修改本地预检+服务端校验兜底（perm_denied 回滚）。玩家可绑定"我的角色"（聊天显示"角色名（玩家名）"）。
- **编辑=完整分页表单**：按创建流程同款分页逐条调整，数据回填后逐页修改、实时联动派生值；禁止"简单回填"式敷衍编辑界面。
- **不存在"初始装备"**：修改场景装备一律是正规背包；创建流程的起始装备选择一次性产出背包内容。
- 开卡流程是独立阶段：生成模式只在新建模式出现；查看/编辑中属性是普通可改数字。

## 背包系统标准（强制）
- **条目化**：装备/道具为长条列表条目（名称/类别/数量/单价/总价/装备状态/效果），条目本身是浮动标签（hover 完整详情），数量可增减；禁止"点选即启用"式一次性控件。
- **装备限制**：装备类物品（护甲/武器/盾）的"装备中"选择限制为背包内已有物品，禁止全量规则表任选（购买时才从规则表选）。
- **套组归类**：套组从规则书定义明确内容，条目化归类展示，标签信息完整（内容清单/总价/说明）。
- **动态价格**：消耗品/卷轴类按规则书公式动态算价（卷轴=选法术+环位自动算价），禁止固定写死或手动填价。
- 金币账本联动：购买扣款、售出加款、负重/容量自动计算（规则书有定义时）。

## 立绘/头像三段流程与资产文件化（强制）
- 流程：上传原图 → 独立窗口先截立绘（3:4 可拖选区）→ 再截头像（圆形）；一张原图产出 data.assets.portrait + avatar/avatarFramed。抠背景色：吸管采样+容差，背景透明化，预览实时。
- **坐标换算铁律**：canvas 预览坐标必须换算回原图像素坐标再 drawImage（记录 fit/dx/dy 换算），禁止把 canvas 坐标当原图坐标。
- **资产文件化**：data.assets 只允许 avatarFramed 与 portrait 两键，与顶层 avatarUrl 一律存 `/Ruler/<系统>/存档/<冒险>/characters/<id>/icon/<文件名>` URL（或空），禁止 base64 dataURL（曾致 2MB 单行）。唯一标准素材=icon/portrait-4x3.png + icon/avatar-1x1-framed.png；无框 avatar、original 原图不落盘不入库。
- 生成链路：立绘工具 canvas 出图 → POST /api/assets/character-image 落盘 PNG → 角色卡存 URL；服务端存档写入前自动迁移遗留 base64/旧路径，产生端禁止再写 base64。
- 主窗口（创建页）只显示立绘结果预览与头像结果，不内嵌裁剪器。

## 职业规则预览
创建/编辑角色卡时，职业分页下方内嵌该职业规则书网页预览（iframe 加载 source/ 或可折叠独立窗口打开原文），职业切换同步切换。

## 背景加值
- 背景分页只负责"选择怎么加"（方案 A/B/C 或自定义），数值分配动态显示在**属性分页**（每属性来源加值汇总：背景/种族/提升等），改动实时联动。
- 骰子值的分配**可拖动**（拖拽到属性槽、可拖回），禁止仅点击式或纯输入式。

## 加点/分配来源面板可交互（通用，强制）
一切规则书的"加点/分配来源"（背景、职业成长、专长、种族等 +N 点数）都按此实现：
- 每个 +N 点数**始终可交互**：未分配槽可拖（draggable）、可点选；已分配槽可点击移除（来源标签 ✕）；方案切换/撤销按钮真实生效（撤销=移除全部已应用加值+恢复可拖空槽），禁止按钮点击后界面无变化。
- **候选与已分配必须分离**：候选只是可选项，绝不自动视为"已分配"；未真正分配到的槽渲染为空槽（可拖），禁止预填候选后显示 used（不可拖）造成死锁。
- 固定基础值时若候选数≤需要数且未分配，自动应用默认候选（上限按规则书）；否则保留空槽等待分配。
- 联动时机：固定基础值、切换方案、撤销、分配后，数值网格/来源面板/派生值立即全部重渲染。

## 界面无布局跳动（No Layout Shift，强制）
- 任何选择操作不得导致下方追加新条目/新块引起界面高度变化（微重构、滚动跳动）。
- 选择结果只允许：①固定区域标题/搜索框旁显示已选标签（同高度替换或常驻一行）②浮动层展示详情 ③已固定高度候选列表内高亮。禁止在列表下方动态插入新描述块。
- 状态变化只改局部文本/类名，禁止整块重渲染导致滚动跳动。

## 环阶/等级解析兜底（通用，强制）
- 规则书定义的"能力环阶/等级"（法术环位、仪式阶、祈唤等级等）解析不得在数据缺失时默认最低档：优先精确查找 → 所在列表分组键 → 按该规则书"获得等级→环阶"规律推导（示例 DND 誓约法术：3/5/9/13/17 级→1/2/3/4/5 环）→ 源文补齐。
- 数据加载完成后**校正已添加记录**：环阶与最新解析不一致的重新解析修正，禁止"先加错再不管"。
- 分类 tab 显示依据该规则书法表/能力列表数据，禁止因个别记录环阶错误凭空出现分组 tab（示例 DND：圣武士无戏法却出现戏法按钮）。
- 名称查找兼容数据键名格式差异：精确失败时前缀/子串匹配，构建 name/fullName 双索引；缺失数据从源文补齐或标注，禁止空描述占位。

## 选择槽效果完整显示（通用，强制）
- 选择槽（职业风格、圣职/职能、超魔法、祈唤、子职业能力等）产生的特性标签必须**携带完整效果描述**（规则书原文），悬停/点击可读，禁止只显示"来源标签"。
- 选项 desc 从规则数据取用；无 desc 回退查找（能力全量数据/源文），仍无则视为数据缺失需补齐，禁止用"标签：名称"充当描述。
- 带前缀的特性名（"风格：X"等）剥离前缀后按名称查效果，禁止整名查找失败即空描述。

## 法术选择动态化
- 可选法术受**职业法表**限制（自动来自规则书压缩产物），法表外不可选（手动自定义入口除外）。
- 按当前等级**动态计算可选数量**（戏法数/准备数/环位上限按规则书公式），**可视化显示**（已选/上限/剩余，超限红色警示）。
- 法术条目标签=**完整法术信息**（环位/学派/施法时间/距离/成分/持续时间/完整描述），悬浮或点击展开全文，禁止简报式截断；数据缺失从源文补齐后交付。

## 角色列表分类分页（宿主）
- 宿主角色列表按分类分页（玩家/友方/敌人/NPC+动态自定义分类），每个 token 带 category 字段；条目旁显示关键信息（等级/职业/HP/AC/状态），放不下的信息用悬浮窗补全。
- 点击地图头像或角色条目只做**选中与定位**；必须通过条目内明确的「角色卡」按钮打开独立窗口（sheet.html）。主窗口不内嵌长详情。

## GM 版本备份（宿主+服务端）
- 角色卡每次保存自动把上一版本存档为 GM 原始版本备份（`Ruler/<系统>/存档/<冒险>/characters/<id>/`：current.json + versions/<时间戳>.json）。
- GM 面板/角色卡页面提供"历史版本"入口：版本列表、任意两版本字段级差异对比。

## 频道提示词多行（宿主）
频道提示词是多行文本，编辑界面必须是多行 textarea 弹层，禁止浏览器单行 prompt()；频道 tab 悬浮预览多行显示。

## 独立窗口（大型功能/查看型内容）
- 大型功能或需要空间的功能（规则树导航、角色卡、源文阅读、长表单、批量工具）实现为独立窗口页面：app/ 下独立 html + window.open（宿主 WebView2 接管为原生窗口），禁止塞进主窗口小容器、弹层或内嵌滚动区。
- 判定（满足其一）：需超过半屏空间；长内容阅读；专注表单填写；与主界面并列使用；批量操作。
- 独立页约定：URL 参数化（?system=&id=&file=）；同源 localStorage+storage 事件与主窗口通信；需要插件能力时页面内加载插件代码（轻量 PluginAPI）；通用机制照常使用。
- 主窗口只保留入口按钮与紧凑列表；查看型内容（角色卡详情、速查原文）必须独立窗口，禁止网页内弹层或内嵌长滚动区。

## 词条悬停预览
词条类内容（法术/物品/专长/状态等）支持鼠标悬停显示效果摘要（绝对定位悬浮层，不改变布局），数据来自规则压缩表或 /api/rules/index；可复用宿主 .term-tip 样式。

## 规则专属角色卡编辑器（Character Builder）
- 每个规则系统提供该规则专属的角色卡创建界面：AI 理解规则书后设计字段、校验、自动计算、来源追踪与动态增删。
- 实现为插件 `Ruler/<系统>/plugins/character-builder/`，manifest.json 的 type 用 character-sheet。
- 要求：字段来自规则书实际章节；派生值自动计算；输入校验；多角色保存/加载；用真实规则数值创建样例角色验证。

## 扩展整理归纳（Rulebook Consolidation）
- 解析阶段（及已解析系统的后续小规模迭代）识别**扩展/更新内容**（扩展书、补丁、新增职业/子职业、旧版章节、新法术/物品/专长等）并归类归纳；分类名按该书实际结构决定，禁止硬编码固定分类。
- 产物：`Ruler/<系统>/compressed/rule_categories.json`（分类→条目及 source 路径）+ 追加归纳表到 compressed/rule_tables.md；source/ 原文件绝不移动或改写。
- 已解析系统禁止重新解析，只做小规模迭代：读索引→识别扩展内容→写入归纳→抽查正例/空例验证；每个分类至少抽查1条 source 路径真实存在，不存在的必须修正后再交付。
