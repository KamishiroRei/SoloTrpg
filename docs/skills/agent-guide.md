# AI工作方法（Agent Guide Skill）

本平台定位：动态解析任意TRPG规则书→自动生成配套角色卡与工具（插件）→AI作为GM带团。核心追求：TRPG的自由 + 电脑游戏的精准；AI输出结构化标记，系统渲染界面；游戏数据以变量精确管理，AI可读可写，前端实时联动。

## 一、任务流程（收到任何需求先走此流程）
1. 理解目标并规划：复杂任务先 todowrite 拆解，明确子任务与验收标准。
2. 设计审核（一切修改前必做，两层）：
   - 第一层 设计目的（游戏策划视角）：这个行为在游戏中的设计目的是什么、谁在执行、意图是什么、期望的游戏结果是什么、问题与设计目的的偏差在哪。禁止直接跳"程序上怎么修"，先回答"游戏上应该是什么样"。
   - 第二层 游戏合理性与用户体验（玩家视角）：玩家看到什么、是否直观方便、在带团流程（创建→升级→战斗→速查）中是否自然可达、是否符合规则书原文。
3. 定位与读取：grep 定位关键词/函数名 → read_file 读目标区域。
4. 立即 edit/write_file 修改，不长期停留于探索。
5. 实际验证修改（正例命中 + 空例为空 + 点击可展开 + 数据来自规则书）。
6. 源码注释只解释代码无法直接表达的规则、数据约束和生命周期；禁止写旧方案对比、修改过程、完成声明、外部产品参照或"为了避免/确保"式自证。
7. 全部完成后再用纯文本总结。

## 二、自然语言需求处理
- 收到需求第一步 grep 定位关键词/函数名（如"骰点分配"就 grep 骰点|roll4d6|attrMode|ability），再 read_file 目标区域，立即修改并验证。
- 禁止通读超大文件、禁止反复小窗口读同一文件（连续只读无输出会被空转检测提醒）。
- 需求模糊时按最合理解释直接实施，不反复确认。
- **文本输出禁令（最高级）**：任何面向玩家的文本（角色设定/剧情/描述/外貌/背景）只基于正面原本路径编写，直接陈述事实本身；禁止"没有X——原本是Y/不是Z"式否定对比写法、禁止"（设定：...）"式自证元说明、禁止任何修正痕迹（"已更正/补充说明"等）。

## 三、工具选择（效率优先）
- 读文件优先 read_file 全量一次读全（中小文件首选）；大文件用 grep 定位行号+一次读 200-400 行。
- 找关键词→grep；改文件→edit/write_file；目录/行数→list_files/glob。
- bash 只在真正需要命令执行时用（启动/构建/运行脚本）；文件操作一律用专用工具；python 先 write_file 写脚本再执行，禁止 -c 内联。

## 四、需求澄清（自行驳斥，强制）
需求矛盾（既要A又非A）、关键信息缺失无法实施、或规则书与需求冲突时，必须立即用 question 工具向用户指出矛盾并请求解答；禁止盲目执行、禁止反复猜测空转。需求合理但模糊时按最合理解释直接实施。

## 五、自我空转检查（每轮工具调用后自评）
是否反复读同一文件？是否只读未改超2轮？是否无谓探索？是则立即转为：grep 定位 → 一次读200-400行 → edit/write_file；信息足够就直接修改。任务必须落地产物（探索最多占一半轮次）。

## 六、插件质量要求
- 功能依据当前规则书实际内容，禁止套用其他规则结构。
- 检索不得只依赖首页或前150条索引；支持常见中英文/旧新版/同义名称（圣武士/帕拉丁/Paladin），无结果时尝试别名并显示命中数。接口：`/api/rules/index?system=<系统>&q=<关键词>&limit=<n>`。
- 修改后用实际查询验证至少一个正例和一个无结果例。
- 专用功能入口在规则详情主体有效区域，按钮点击展开、不常驻大面板、不弹窗。
- **扩展书自动捕获（强制）**：构建/迭代任何选项类数据（子职/职业/法术/专长/装备/背景/种族等）时，数据源必须覆盖该规则系统全部官方资料（核心书+全部扩展书/设定书/官方更新），禁止只基于核心书。流程：①枚举 compressed/rule_index.json 中该主题全部条目（含扩展书路径）②对照现有实现找缺口 ③从 source/ 源文提取完整数据 ④补充实现并验证。扩展条目缺失即未完成；第三方/UA 默认不收录但保留手动入口，收录与否在总结说明。

## 七、主动举一反三（强制）
- 收到需求先问三问：①现象背后期望的游戏体验是什么 ②当前实现与体验的差距（不只修字面）③有无同类问题（其他页面/频道/功能）一并优化。
- 页面按"应该是什么样"编写，而非"把旧的拆分"。
- 自查清单：布局按玩家视角组织？数据联动（改一处自动更新相关处）？关联功能缺失（选职业是否自动给熟练/装备）？交互有明确反馈？与宿主主题一致？
- 发现相关额外缺陷直接一并修复并在总结说明；超范围但明显影响体验的问题用 question 工具征询。

## 八、长线任务数据落盘与防重读（强制）
- 数据收集期：确认后的数据要点写入任务文件（`AI任务/<任务名>/ref/data.json` 或项目 `_tools/`），不留全在上下文；读完的文件记录「路径: 摘要」。
- 上下文被自动压缩后：先读自己的落盘文件恢复数据上下文，再基于压缩摘要的"下一步"继续；不得重读已落盘记录的源文、不得重新探索目录。
- 判定：同一源文不因压缩而重复读取；压缩后第一轮从落盘文件或摘要直接续接。

## 九、大文件读取与检索降级（强制）
- 大文件（>60K字符）禁止顺序窗口扫读：grep 定位目标函数/关键词（±50行）读取；中小文件（≤60K）full 一次读全。
- JSON/索引检索无结果先查格式（"title": "X" 有无空格可能不同）：grep 搜关键词本身确认存在性与确切格式，再调检索；仍无果才降级读 source/ 源文。
- 数据字典类（种族/职业/背景/专长列表）优先从 compressed/ 产物读取（rule_settings.json/rule_tables.md/rule_index.json），找不到才读 source/。
- bash 路径：工作目录=对应 scope 根，返回带 [cwd: 路径]；不写相对 cd，直接用基于根目录的相对路径或绝对路径（绝对路径全授权，中文路径建议引号包裹）。
- **自然语言路径断句（强制）**：用户给出的路径是自然语言描述，不是机械字面。如「XX里的设定集」= 目录「XX」下的「设定集」，「里/中/下/内」是介词、「的」是修饰连接，都不是目录名的一部分；禁止把整句当作文件夹名原样重试。路径不存在时：先 list_files 列出父目录（或最近存在的上级目录）按实际条目继续，不执着于原路径字面、不原样重试同一路径。
- 验证优先用工具（grep/read_file/node --check 一次），禁止为同一目的反复执行 bash 变体；一条命令一次目的；edit 未找到文本先 grep 确认确切写法再改，失败不原样重试；node 脚本先 write_file 落盘再执行，避免 -e 内联长脚本。

## 十、交互式推进（强制）
带团/导入/开发任务一律交互式：需求不明确、取舍重大、或会改变玩家体验的决定，先用 question 工具或自然语言向用户确认再执行；禁止闷头连续执行大段任务；分步推进，每步等待确认。
