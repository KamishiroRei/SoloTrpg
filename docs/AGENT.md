# TrpgRecode 网页版开发 AGENT

## 1. 项目定位

TrpgRecode 是个人开发并开源的轻量 TRPG 平台，本质是“为了跑团而生、能让 AI 自主读取规则书并继续开发自身的套壳 OpenCode”。

用户导入规则书、扩展资料或模组后，AI 必须能够主动读取、研究、整理、设计、编写和验证对应规则模块，让资料逐步变成真正能运行的跑团系统。

主要场景只有两类：

- 单人跑团：AI 担任 GM，负责叙事、扮演、判定、规则调用和状态管理。
- 熟人联机：简单直接的 P2P 联机，AI 可担任 GM，也可作为副 GM 辅助真人 GM。

不建设公共大厅、陌生人匹配、账号中心、商业后台或大型在线服务。

## 2. 最高原则

### 主动思考

收到任务后，先理解用户真正想完成的跑团行为，而不是机械修改字面问题。必须主动检查：入口、操作流程、规则来源、数据变化、AI 调用、保存恢复、刷新重进、联机同步、错误反馈，以及同一根因是否影响其他入口。

### 主动完善

功能要真正可用时，主动补齐直接相关的入口、界面、数据、计算、存档、AI 工具、热重载和日志链路。不得为了省事把任务缩成最小改动，也不得借机加入公共平台、复杂账号、企业权限等无关系统。

### 游戏体验是唯一完成基准

按钮存在、页面能开、接口能调、语法通过都不代表完成。只有真实玩家能顺畅、明确、稳定地完成对应跑团行为，且结果符合规则、数据立即变化、AI 能继续使用、刷新与联机后仍正确，才算完成。

### 禁止穷举方案（通用工程原则，强制）

任何地方（规范条款、代码逻辑、工具设计、界面组织、数据组织）一律优先用「判断原则 / 机制驱动 / 数据驱动」表达；穷举式分类（"XX类=必须做Y"式清单、硬编码场景枚举、逐条打补丁）视为缺陷。允许例外：无法归纳的边界场景（安全白名单、固定枚举、权限表）。新增任何条款/逻辑前自检：这是"判断原则"还是"穷举清单"？后者即改写或改设计。详见决策记录 [20260807-禁止穷举方案-通用工程原则](../../知识库/决策记录/20260807-禁止穷举方案-通用工程原则.md)。

## 3. 当前开发重点

宿主框架已接近完成，当前主要开发对象是 DND 模式。DND 是第一套完整参考规则环境，也是验证规则书解析、角色管理、判定、战斗、AI GM、存档和联机能力的实际测试场。

DND 专属规则、数据、页面和视觉必须留在 `Ruler/DND五版不全书/`。当 DND 暴露出所有规则系统都可能需要的能力时，再提炼为宿主接口；不得把 DND 字段和视觉伪装成通用宿主设计。

## 4. 模块边界

宿主负责通用运行能力：AI 接入、对话与工具调用、文件与规则资料检索、插件热重载、角色/会话/模组/存档容器、通用窗口与地图、P2P 联机、日志和调试。

规则模块负责规则专属内容：属性与派生值、角色创建成长、职业种族背景、技能特性法术、装备物品资源、判定战斗状态恢复、规则页面与规则专属 AI 工具。

唯一后端入口是 `server/server.js`。开发版与发布版共享核心逻辑，不建立第二套 Flask、Python 或其他后端。

宿主不得写死规则名称、角色卡结构、属性职业、页面数量、操作顺序、颜色主题或固定美术风格。

## 5. AI 开发闭环

每次开发形成完整闭环：

定位 → 读取 → 理解 → 设计 → 修改 → 热重载或快速重启 → 验证 → 总结

系统频道使用“最小基础提示词 + 动态 SKILL”：

- `agent-guide`：开发闭环、工具选择和验证方法。
- `rulebook-development`：规则书解析、正式规则数据和模块边界。
- `character-system`：角色卡、背包、标签、权限、历史版本和素材。
- `gameplay-ux`：玩家流程、页面层级和交互体验。
- `plugin-authoring`：插件接口、加载、卸载和热重载。
- `gm-protocol`：AI GM、副 GM、判定和数据更新。

不得把所有规范永久塞进唯一固定提示词。频道提示词必须以多行文本编辑和显示。

## 5.1 双模式体验定位（SillyTavern × opencode，强制）

TrpgRecode 是 SillyTavern（玩家侧跑团体验）与 opencode（系统侧开发体验）的结合体，两类频道体验边界不可混淆：

- **玩家频道（剧情/战斗/自建）＝ Silly 式聊天流**：消息气泡 + 打字指示器 + 私聊区分场内外（GM 指令窗口）+ 无思考细节。AI 思考/工具内容一律不显示（防剧透），只允许显示"💭 AI思考中"与简短进度。
- **系统频道 ＝ opencode 式开发台**：AI 开发 Agent、工具调用步骤、轮次、tokens、推理摘要。
- **AI 思考状态分层（强制）**：全界面文案统一"AI思考中"；状态条内嵌于聊天栏（不浮窗）。开发任务（系统频道/规则书解析/模组整理）显示完整细节；带团模式按 AI 角色分层——副GM/规则助手给真人 GM 显示进度（正在规划剧情/正在查阅世界资料），AI GM/AI 玩家隐藏进度；停止按钮常驻输入行，主机任何时刻可中止 AI。AI 只在主机运行，联机其他客户端不显示 AI 状态。
- **输入行状态区**：显示"谁正在输入"（联机玩家：XX 正在输入…/XX、YY 等 N 人正在输入…；AI：AI思考中/AI执行XX 简短条目，XX 为工具名简写，无路径无参数）。
- **消息路由纪律**：带团操作反馈（开团/暂停/继续/错误/中断）留在当前频道；只有开发任务类消息进系统频道。不得再把用户操作反馈塞进系统频道。

## 6. 角色系统统一规范

### 创建、查看与编辑

角色创建、查看和编辑必须读写同一份角色数据，并复用同一规则组件。查看页面默认只读，角色拥有者和 GM 可在角色卡原位进入编辑；不得维护一套“角色详情”和另一套风格、字段不同的“修改角色卡”。

编辑现行角色卡时：

- 属性是可直接修改的最终数字，不出现投点、购点或骰点模式。
- 装备是正规的现行背包，不出现“重新选择初始装备”。
- 核心属性、HP、AC、先攻、速度等高频数据常驻总览；已在总览完整显示的种族、属性不得再建立重复分页。职业、背景、技能、法术、背包、特性、状态和笔记按用途分页。
- 自定义背景必须显示真实名称和正式数据，不能只显示“自定义背景”占位。
- 每次保存前自动保留 GM 历史版本，支持字段对比和恢复。
- 弹窗、浮窗和掷骰日志不得互相覆盖或留下无法关闭的遮罩；弹窗支持取消、右上关闭、点击遮罩和 Escape，打开弹窗时收起其他浮动层。

### 地图与角色列表

- 地图点选角色头像只选中右侧角色条目，不打开角色卡。
- 角色条目点击只选中；通过条目中的显式“角色卡”按钮打开。
- 玩家、友方、敌人、NPC 和自定义分类使用分页。
- 可编辑角色拖到分类分页即可改变分类，不在条目中放分类按钮。
- 条目显示核心状态；放不下的信息进入统一浮动详情。

### 背包与装备

物品统一为正式数据条目，至少包含名称、类别、数量、单价、总价、重量、装备状态、来源、完整说明和效果。治疗药水等可直接增减数量；套组展开为明确内容并保留套组来源；卷轴先选法术与环位，再动态计算价格和规则字段。

物品是否可装备必须由物品数据中的装备槽、可装备标记和规则类别决定，不能给所有物品统一添加“装备”按钮；套组、消耗品和普通杂物默认不可装备。护甲只能从背包中已有护甲装备。武器攻击与伤害自动汇总属性、熟练、魔法和效果。负重与携带状态归入背包，不在总览重复堆放。创建时可自动发放初始装备，并至少保留 5 个稳定物品栏位，避免动态增删造成界面跳动与误操作；编辑现行角色时只管理真实背包。

### 标签

法术、特性、装备、状态、效果、熟练等全部使用宿主唯一标签系统 `TrpgTag`。创建页和角色卡不得各自维护不同标签与浮窗。浮窗显示完整规则信息、来源和结构化字段，不使用简报占位。

### 立绘与头像

一张原图依次生成 3:4 垂直立绘和圆形头像。素材输出为 PNG 并保留透明像素；吸管从原图采样背景色，支持容差和边缘柔化。裁剪工具在独立窗口运行，角色卡只显示结果；宿主接管新窗口时不得误报浏览器拦截。

## 7. 自动化标准

平台应比电子表格自动卡拥有更高自动化程度，但不照搬其布局。目标是电子游戏式体验：

- 规则选项按版本、职业、等级、前置和数量动态过滤。
- 背景加值在背景页决定规则，在属性页拖放或调整具体分配，并实时显示结果。
- 法术按法表、等级、施法能力和可选数量自动计算和可视化。
- 装备、金钱、护甲、攻击、伤害、负重、法术位和资源自动联动。
- 所有自动结果保留明确手动自定义入口，但手动入口不能替代自动实现。
- AI、规则模块和前端读取同一份正式数据，而不是从聊天文本猜状态。

## 8. 数据、保存与联机

角色、状态、资源、物品、地图和会话结果必须落为明确数据。页面刷新、后端重启和重新加入房间后能够恢复；单人与 P2P 使用兼容结构；模块代码与玩家存档分离；新增字段有默认值；模块升级不覆盖玩家内容。

房主承载主要游戏状态，玩家操作自己的角色，GM/AI 管理公共信息。聊天、判定、角色变化和必要地图状态同步；短暂断线后可重新加入并恢复。

## 9. 热重载与错误链路

规则模块的页面、样式、脚本、资源和数据应尽量独立刷新；卸载时清理事件、计时器和状态；单个模块失败不能拖垮宿主。关键错误写入 `Logs/`，供 AI 继续读取修复。无法热重载的底层改动集中在少量入口，通过 `start.bat` 快速重启。

`start.bat` 用于本地调试，必须持续显示日志、写入本地日志并自动打开网页；EXE 只用于发布打包。

## 10. 执行与完成边界

收到明确执行要求时，直接修改源码并验证，不只给建议或伪代码。公共接口变更同步所有调用方；不得通过删除功能、清空配置或覆盖存档完成修复。

源码注释只保留无法从代码直接看出的规则、数据约束和生命周期。不得在源码中记录旧方案对比、修改过程、完成声明、外部产品参照或“为了避免/确保”式自证说明；变更原因放入任务记录和交付说明。

一次任务只有同时满足以下条件才算完成：功能真实运行；AI 能找到并调用；模块可加载和重载；界面、规则、数据一致；数据可保存恢复；单人与联机兼容；规则专属内容没有写死进宿主；旧模块与旧存档未破坏；日志足以定位问题；已完成语法和实际流程验证；交付列出修改文件、核心变化、兼容影响和仍未完成内容。

## 角色成长、模组与主持权限

- 职业、子职、战斗风格、超魔、魔契祈唤及其他嵌套选择必须由规则数据生成。创建和修改角色时按等级分页，显示该等级获得的精确规则条目、来源与选择数量。切换职业、子职或选择时，旧来源的能力和法术必须移除，新来源内容写入角色；角色卡最终将结果保存为可快速查阅的完整标签。
- 角色卡中的任何加值都要能追溯来源。背景属性提高必须显示具体属性与数值，技能浮窗显示技能定义、关联属性和精确原文路径。概览只保留高频信息，负重归入背包，功能按钮放在玩家最容易操作的顶部区域。
- 模组导入只放在规则页。原始资料复制到 `Ruler/<规则系统>/modules/<模组名>/`，同时生成模组 manifest、AGENT、索引占位与持久 AI 任务。导入后由系统开发 Agent 读取原始资料并建立场景、实体、线索、遭遇、媒体和规则链接；GM 面板不再重复提供导入入口。模组导入必须按主题拆解为 `资料/` 多文件资料包（故事大纲/NPC/怪物/遭遇/地点/物品/线索/秘密/时间线等，稳定 ID，见 module-ingest.md「拆解重组」），图片解包至 `assets/` 并语义化命名；AI 带团按需读取拆解文件，禁止每次全量重读原始 PDF；进入新场景时查媒体索引自动播 CG/换地图背景。
- 房主只负责承载房间，不自动等于真人 GM。GM 工具、模组秘密、AI 主持和全局裁定权限只授予当前真人 GM；非 GM 包括房主玩家都只能看到 GM 帷幕。房主可以明确指定真人 GM。
- AI 运行身份分为 AI GM、AI副GM、AI玩家（AIPL）和规则助手。AI副GM服从真人 GM 的最终裁定；AIPL 只扮演被分配的玩家角色，不读取 GM 秘密、不调用 GM 工具。
- GM 面板只放带团工具。模组插图以可搜索、可预览、可选择的图库呈现，不要求 GM 手工输入程序化资源路径。

## 多地图、范围与地图标记

- 地图是底层画布；聊天栏与右侧面板处于同一浮动层，地图工具栏在其上方。浮动界面不得改变地图尺寸或坐标系。
- 顶部地图分页管理小队、场景、区域和世界地图。每张地图独立保存背景、比例尺、Token、范围与测量结果，并在单人存档和联机房间中同步恢复；当前分页、平移和缩放属于各玩家的本地视图，不得因一人操作而拉动其他人的镜头。
- 地图背景、网格和比例尺只在当前地图设置中管理。范围与测量输入真实距离和单位，由当前地图“1格=实际距离”换算，不把格数暴露为规则输入。
- 左键选择或拖动对象，右键拖动地图。R/M 只切换工具；随后用左键在点击位置开始，第二次左键固定。范围在点击位置显示上下文面板，可修改类型、距离、单位、颜色、材质、透明度、说明与删除。
- 地图 Token 是独立于角色的通用标记，可表示物体、小队、地点、危险和注释。通用 Token 不进入角色列表、先攻和角色持久资产；角色 Token 与地图标记必须使用不同的数据类别。

## 模组公开与保密

- 规则书源码目录即使名为“模组”也不是已导入模组。只有 `Ruler/<规则系统>/modules/<模组名>/.trpg/module-manifest.json` 登记的目录才能进入模组列表。
- 导入后的原始资料默认仅 GM、AI GM 和获授权的 AI 副 GM可检索。玩家与 AIPL 只能读取 `.trpg/public-index.json` 明确公布的文件；没有公开条目时玩家端不显示该模组。
- AI 整理模组时必须建立 GM 私有索引、公开索引、稳定实体/场景 ID 和发布状态。公开是逐条、可追踪的状态变化，不得通过暴露整个原始目录实现。

## 规则选择组件统一

种族、职业、子职业和嵌套能力必须复用同一种自适应规则卡、规则条目、选择区和来源浮窗。职业不得另建一套低效布局；其 1—20 级成长、战斗风格、子职业、固定法术和嵌套选择都使用同一组件体系。4级、8级等职业成长必须表现为明确的规则选择条目，先在“属性提升 / 专长”等规则分支中选择，再填写具体属性或专长；选择变化后自动撤销旧效果、应用新效果，并保存来源记录。

## 自动提示词注入与规则解析标准

- 系统频道、规则书解析、世界书解析、模组导入、角色系统与界面重构不再依赖 AI 自己“想起来调用 SKILL”。后端必须按任务类型自动注入默认提示词与必要 SKILL；AI 可按需再用 `skill` 工具重读某项规范，但不得因未手动调用而降低标准。
- 默认提示词模板保存在 `docs/prompts/`：`system-development.md`、`rulebook-ingest.md`、`rulebook-development.md`、`module-ingest.md`、`character-system-development.md`、`gameplay-ux-development.md`、`gm-runtime.md`。模板是多行文本，可持续迭代；不得把所有长规范写死成单行前端 prompt。
- SKILL 规范文档保存在 `docs/skills/`（`agent-guide.md`、`rulebook-development.md`、`character-system.md`、`gameplay-ux.md`、`plugin-authoring.md`、`gm-protocol.md`、`gm-standard.md`），server.js 启动后 lazy 读取并缓存（`loadSkillFile`），可按需独立编辑，禁止再内联进 server.js。
- **宿主新能力上线必须同步告知目标 AI（强制）**：任何新增的宿主 API/机制/交互（如角色卡导出导入、冒险重置、typing、状态条分层）上线时，检查它是否影响 AI 的开发行为或带团行为——影响的（AI 需要知道才能正确开发/带团）必须同步写入对应 docs/skills/*.md 与 docs/prompts/*.md；纯界面呈现（无需 AI 感知）可跳过，但要在任务记录里说明为何无需告知。

## 5.2 通用框架原则（强制；一切功能自动引申最大化）

**宿主只提供通用原语与自由链路，不预置任何规则书功能；任何规则书功能（反应、借机攻击、准备动作、专注、突袭、护盾、环境效果、世界事件……）都由 AI 用原语为该书动态建立。** 本原则适用于全部功能域，不限于战斗：

- **宿主侧原语集**：事件总线（emit）· 规则引擎（trigger/hook 触发 + 条件/概率/权重/冷却）· 动作原语（speak/move/delta/set/ask/emit/handoff）· 询问弹窗（ask）· 接管（handoff）· 回合状态机（行动者/轮转/胜负，规则书可关）· 轮次协议（T1/T2/T3 省 token）。
- **规则书侧数据**：一切具体功能 = `data.behavior` 规则 + `compressed/rule_combat.json` 配置/模板，AI 用 gm_update 动态建立与修正。DND 的"反应"只是 ask 原语的一个用例。
- **配置驱动**：引擎启动战斗读 `rule_combat.json`（reactionPool/battleEnd/hooks/templates）；新规则书无该文件 → 中性通用默认（不套任何规则书结构）；模板标注规则书名，禁止跨书套用。
- **引申要求**：设计或修改任何宿主功能时，先问"这是通用原语还是规则书功能"——通用机制进宿主（原语级），具体功能进规则书数据（AI 可改）；发现"相似性质"的新需求（新的询问型交互、新的事件时点），优先复用既有原语而非新增宿主特化代码。详细规范见 docs/skills/gm-protocol.md「十六、通用框架原则」。
- **控件交付自查（强制）**：任何 UI 改动（宿主或插件，哪怕一个按钮）交付前必须逐项自查——排版平行对齐且无注释式说明、状态化（禁用/隐藏/联动实时刷新）、点击有可见反馈、真实玩家流程无死路、极端情况合理；任一条不满足即未完成。历史教训：设置页按钮曾以粗糙两行+注释式 hint 交付（默认冒险无禁用态、不联动）。详细清单见 docs/skills/plugin-authoring.md「控件交付自查」。
- 规则书或世界书导入后，解析 Agent 自动使用 `rulebook_ingest` 任务提示词，并注入 `agent-guide`、`rulebook-development`、`gameplay-ux`、`character-system`、`plugin-authoring`。任务目标是把资料变成可运行规则模块，不是只生成摘要或目录。
- 模组导入后，模组资料复制到 `Ruler/<规则系统>/modules/<模组名>/`，并自动使用 `module_ingest` 任务提示词发送给系统开发 Agent。模组整理必须生成 GM 私有索引、公开索引、稳定场景/实体/媒体 ID、AGENT 和验证记录；玩家与 AIPL 只能读取公开索引明确公布的内容。
- DND 只能作为“完成度与体验质量”的参考：自动计算链、来源追踪、标签浮窗、背包、角色成长、AI 可读数据、保存恢复和联机一致性。不得复制 DND 原始代码、字段、规则名、美术或专属判断到其他规则系统。
- 新规则系统的字段、页面、视觉、交互、术语和信息密度由该规则书决定。宿主只提供挂载、热重载、日志、文件工具、通用标签、窗口和联机容器。
- AI 开发 Agent 的写入工具在当前规则系统内可操作 `compressed/`、`plugins/`、`modules/`、`tasks/`、`ui/` 等正式产物目录；`source/` 与 `original/` 是原始资料目录，禁止作为整理结果覆盖写入。

### 角色创建与成长的本轮固定标准

职业、子职业、专长和法术默认读取官方规则扩展；第三方、同人或自制资料必须由 GM 或开发任务显式开启。子职业选择页只显示简洁介绍，完整成长按等级拆分到对应等级页；角色等级只决定哪些规则写入角色，不能擅自改变玩家正在查看的等级页；超过当前等级的页面可以查看，但不写入角色。切换职业、子职业、背景或起始装备方案时，旧来源赠送的物品、特性、法术和加值必须先撤销，再应用新来源，不能把已经不存在的选择残留在背包或角色标签里。

开卡装备界面是背包列表，不是装备芯片墙。玩家通过物品名输入和数量添加物品，系统自动匹配类别、价格、来源、是否可装备和悬浮详情。金币扣除只属于开卡采购或交易行为；编辑现行角色卡时手动添加背包条目不自动扣钱。背景提供的属性加值在属性页配置，并显示具体属性、加值、应用前后和来源。骰点候选固定预留 5 条横向行，避免动态伸缩导致误操作。

- 职业、子职业、专长和法术默认读取官方规则扩展；第三方、同人或自制资料只在显式开启后进入候选。专长和法术标签必须显示规则详情、来源与必要前置，不能显示“由规则资料提供”之类的占位文本。被选法术列表必须固定在法术页顶部，环位切换只改变候选区，不改变已选区位置。
- 子职业介绍只写简短定位；完整特性、固定法术和嵌套选择按获得等级放入对应等级页。职业页不得显示“到达该等级后”“高于当前等级”之类机械提示，电子游戏式界面只展示可操作规则与结果。
