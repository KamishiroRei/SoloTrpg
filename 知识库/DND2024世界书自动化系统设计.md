```

             始终激活条目注入                  系统层预投骰     <dice>/<battle>  自动patch    →卡片/面板
```

|----------|-----|---------|---------|

| after_char | 1 | 角色定义后 | -- |

### 关键设计原则

1. **微内核GM**: 透明系统层, 不具有人格, 只执行规则判定
2. **双通道输出**: 叙事通道(角色所见所闻) + 机器通道(`<dice>`, `<battlecheck>`, `<UpdateVariable>` 等结构化区块)
3. **最小写入策略**: 变量更新只写"本次变化"字段, 缺省由stats引擎自动补全
4. **零token骰子**: 骰值由 `{{roll:}}` 宏在系统层预生成, AI只读取结果

## 二、变量系统 (MVU 架构)

### 2.1 变量树结构

以 `/角色列表/{角色名}/...` 为根路径的树状存储:

```
角色列表/{角色名}/
├── 基础信息/ (姓名, 种族, 体型, 阵营, 语言, 外貌, 性格, 背景)
├── 等级: number
├── 熟练加值: number
├── 属性/ (力量, 敏捷, 体质, 智力, 感知, 魅力: 1-30)
├── 生命值/ (当前, 最大, 临时, 生命骰)
├── 护甲等级: { 总值, ... }
├── 速度: { 基础, 当前 }
├── 熟练配置/
│   ├── 技能: { 隐匿: "p", 游说: "e", 察觉: "j", ... }
│   ├── 豁免: { 感知: true, ... }
│   └── 武器, 护甲, 工具
├── 状态/{状态名}: { 存在, 等级?, 持续时间, 来源, 效果描述 }
├── 资源/{资源名}: { 当前值, 最大值, 恢复规则, 描述 }
├── 施法/
│   ├── 法术位/{1-9环}: { 当前, 最大 }
│   └── 法术书/{法术名}: { 准备中, ... }
├── 物品/
│   ├── 武器/{名}: { 伤害公式, 伤害类型, 映射属性, effectTags }
│   ├── 护甲/{名}: { 护甲类型, 基础护甲值, effectTags }
│   └── 奇物/, 杂物/
├── 特性/{职业|种族|专长}/{特性名}: { 描述, effectTags, effects }
├── 武器专精, 钱币
└── 笔记/{标题}: { 内容, 任务?, 地点?, 时间? }
```

### 2.2 变量更新机制 (JSON Patch 扩展)

**协议**: 基于 RFC 6902 JSON Patch 的自定义扩展
**触发**: 每条回复末尾自动输出 (Entry 11, `constant=true`, `order=0`)

**输出格式**:
```
<UpdateVariable>
<Analysis>
- Time passed: {时间流逝}
- Dramatic updates: yes/no
- {逐字段变化分析}
</Analysis>
<JSONPatch>
[
  { "op": "replace", "path": "/角色列表/艾尔玛/生命值/当前", "value": 22 },
  { "op": "delta",   "path": "/角色列表/艾尔玛/生命值/当前", "value": -8 },
  { "op": "insert",  "path": "/角色列表/艾尔玛/物品/武器/长剑", "value": {...} },
  { "op": "remove",  "path": "/角色列表/艾尔玛/物品/武器/旧武器" }
]
</JSONPatch>
</UpdateVariable>
```

**支持的操作**:

| 操作 | 说明 | 示例 |
|------|------|------|
| replace | 替换已有路径值 | HP 30 -> 22 |
| delta | 数字路径增减 | 受8点伤害 -> -8 |
| insert | 插入新项 (- = 追加末尾) | 获得新武器 |
| remove | 删除路径 | 消耗物品 |
| move | 移动路径 | 物品转移 |

**绝对铁律**:
- 所有path必须以 `/角色列表/{角色名}` 开头
- {角色名} 必须已存在于变量树中
- 禁止: `/角色列表/状态/力竭` -- "状态"不是角色名
- 正确: `/角色列表/艾尔玛/状态/力竭/等级`

### 2.3 技能熟练度最小表示法

```
熟练配置:
  技能:
    隐匿: "p"    # proficient (熟练)
    游说: "e"    # expertise (专精)
    察觉: "j"    # jack of all trades (半熟练)
```

**值映射**: "p"/1/+5p -> 熟练 | "j"/0.5/+3j -> 半熟练 | "e"/2/+7e -> 专精 | 0/删除 -> 无
**规范技能名**: 运动, 特技, 巧手, 隐匿, 奥秘, 历史, 调查, 自然, 宗教, 驯兽, 洞悉, 医药, 察觉, 求生, 欺瞒, 威吓, 表演, 游说
**兼容别名**: 体操=特技, 生存=求生, 说服=游说, 医疗=医药

### 2.4 EffectTag 效果预设系统

**设计理念**: 用简短规则键代替冗长effect数组, 减少token消耗

**可用键**:
```
ac_plus_1, save_plus_1, skill_plus_1, hp_plus_5,
spell_dc_plus_1, spell_attack_plus_1,
weapon_attack_plus_1, weapon_damage_plus_1, weapon_damage_d4
```

**effect最小写法** (仅effectTag覆盖不到时使用):
```yaml
effects:
  - target: "initiative.bonus"
    mode: "add"
    value: "@pb"
```

**常用target**: ac.bonus, initiative.bonus, speed.bonus, hp.max, save.all, skill.all, skill.{技能名}, spell.attack, spell.dc, weapon.attack, weapon.damage, weapon.damage.dice
**value表达式**: @pb, @level, @strmod, @dexmod, @conmod, @intmod, @wismod, @chamod

### 2.5 物品系统最小字段

```
武器: { 伤害公式, 伤害类型, 映射属性?, effectTags?, effects? }
护甲: { 护甲类型, 基础护甲值, effectTags?, effects? }
奇物: { 描述?, effectTags?, effects? }
```

映射属性不写默认按力量; 两用武器按实际使用属性

## 三、骰子系统

### 3.1 骰子序列预生成 (Entry 643316)

**设计目标**: 零token消耗 -- 骰值由droll库在系统层预生成, AI只按序读取

**预生成内容** (每轮20组):
```
<dices>
d20: [1:(15)|2:(7)|3:(20)|4:(3)|...|20:(11)]
d6:  [1:(4)|2:(2)|3:(6)|...|8:(6)]
d4:  [1:(3)|2:(1)|3:(4)|...|8:(3)]
d8:  [1:(7)|2:(4)|3:(2)|...|8:(8)]
d10: [1:(9)|2:(3)|3:(6)|...|8:(1)]
d12: [1:(11)|2:(5)|3:(8)|...|8:(2)]
</dices>
```

**使用规则**: 严格按1->20依次消耗 | 用完从1循环 | 每条新回复重新生成 | 非d20仅用于伤害骰

**底层引擎**: droll.js (npm: droll@0.2.1)
- `droll.validate("2d6+3")` -> 验证表达式
- `droll.roll("2d6+3")` -> `{ rolls: [3,4], modifier: 3, total: 10 }`
- 正则: `/^([1-9]\d*)?d([1-9]\d*)([+-]\d+)?$/i`

### 3.2 掷骰检定UI (Entry 781421)

**触发**: 发生检定/豁免/攻击掷骰时
**渲染**: `<dice>...</dice>` -> 前端正则解析 -> 检定卡片

**严格6行格式**:
```
<dice>
发动技能: {技能名/检定类型}
目标: {目标角色}
情境: {叙事描述}
检定细节: d20({裸骰}) + {加值}({来源}) = {总值} vs DC {DC值}
判定结果: {大成功|成功|失败|大失败}
结果描述: {叙事结果}
</dice>
```

**判定规则(绝对)**:
- 裸骰=20 -> 大成功/Critical Success (加值无关! 总值30但裸骰非20也不算)
- 裸骰=1 -> 大失败/Critical Failure
- 其他 -> 成功或失败

### 3.3 战斗检定UI (Entry 781422)

**触发**: 战斗中攻击/伤害/豁免/先攻/专注维持判定
**渲染**: `<battlecheck>...</battlecheck>` -> 战斗检定卡片

**严格7行格式**:
```
<battlecheck>
发动者: {攻击方}
目标: {防御方}
行动: {行动名称}
检定类型: {近战攻击|远程攻击|法术攻击|范围豁免|专注维持|先攻排序}
检定细节: {骰式与结果}
判定结果: {命中|未命中|豁免成功|豁免失败|...}
战果描述: {叙事描述}
</battlecheck>
```

**合并规则**: 攻击+伤害合并 | 范围豁免+伤害合并(多目标写入战果描述) | 先攻排序合并 | 纯伤害可不合并
**标准结果词**: 大成功/成功/失败/大失败/命中/未命中/豁免成功/豁免失败

### 3.4 骰子数据流

```
{{roll:1d20}}宏 -> droll.js预生成(0 token) -> 注入Prompt -> AI按序取骰 -> 输出<dice>/<battlecheck> -> 前端正则渲染卡片
```

## 六、UI渲染正则体系

### 6.1 结构化区块总览

所有区块由前端正则解析渲染, AI只负责按格式输出文本:

| 区块标签 | 用途 | 条目 | 解析产物 |
|----------|------|------|---------|
| `<dice>...</dice>` | 非战斗检定 | 781421 | 检定卡片 |
| `<battlecheck>...</battlecheck>` | 战斗检定 | 781422 | 战斗检定卡片 |
| `<battle>...</battle>` | 战术地图 | 2 | 网格地图面板 |
| `<UpdateVariable>...</UpdateVariable>` | 变量更新 | 11 | JSON Patch后端处理 |
| `<status_description>...</status_description>` | 角色状态 | 6 | 能力面板 |
| `<char_info>...</char_info>` | NPC档案 | 22 | 角色卡片 |
| `<!-- charGenerationThink:... -->` | NPC思考 | 22 | 无渲染(HTML注释) |
| `<dices>...</dices>` | 骰子序列 | 643316 | 纯文本(AI读取) |

### 6.2 正则解析设计原则

1. **文本即协议**: AI不需要理解UI, 只需按格式输出文本行
2. **字段名即Schema**: 每行以 `字段名: ` 开头, 前端按字段名取value
3. **不可逆性**: AI输出的是"事实陈述", 不是"UI构建指令"
4. **容错性**: 未知字段被忽略, 顺序不敏感

### 6.3 伪代码: 前端正则解析

```javascript
// <dice> 区块解析
const diceRegex = /<dice>\s*(.+?)\s*<\/dice>/gs;
const fieldRegex = /^(.+?):\s*(.+)$/m;

function parseDiceBlock(text) {
  const match = diceRegex.exec(text);
  if (!match) return null;
  const fields = {};
  for (const line of match[1].split('\n')) {
    const fm = fieldRegex.exec(line.trim());
    if (fm) fields[fm[1]] = fm[2];
  }
  return {
    skill: fields['发动技能'],
    target: fields['目标'],
    context: fields['情境'],
    detail: fields['检定细节'],
    result: fields['判定结果'],
    description: fields['结果描述'],
  };
}
```

```javascript
// <battle> 区块解析
const battleRegex = /<battle>\s*([\s\S]+?)\s*<\/battle>/;
function parseBattleBlock(text) {
  const match = battleRegex.exec(text);
  const units = [];
  for (const line of match[1].trim().split('\n')) {
    const [id, ...fieldParts] = line.split('|');
    const fields = {};
    for (const part of fieldParts) {
      const [key, ...value] = part.trim().split(/\s+/);
      fields[key] = value.join(' ');
    }
    units.push({ id: id.trim(), ...fields });
  }
  return units;
}
```

```
  v
```

## 八、设计模式总结

### 8.1 核心模式

| 模式 | 实现 | 条目 |
|------|------|------|
| 顺序状态机 | 严格逐步交互, 每步等待输入 | 开始流程(5) |
| 观察者模式 | 监听每条回复, 自动生成Patch | 变量更新(11+781420) |
| 策略模式 | RAW规则 vs 合理化原则的双轨 | DM协议(9+16) |
| 装饰器模式 | 包裹原始文本输出结构化卡片 | 检定UI(781421/2) |
| Pipes&Filters | 骰子序列->LLM->UI渲染管道 | 643316+781421/2 |

### 8.2 扩展接口规范

新增功能需遵循:
1. **结构化区块**: `<标签>...</标签>` 包裹, key: value 格式
2. **变量更新**: `/角色列表/{角色名}/...` 路径规范
3. **effectTag**: 优先预设键, 覆盖不到才写effects
4. **物品最小字段**: 只写"会影响计算"的字段
5. **骰子引用**: 用 `{{roll:}}` 宏, 不让AI生成随机数
