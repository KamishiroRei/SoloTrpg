# D&D规则 → 自动化车卡界面：设计方法论

> 分析对象: `D&D 2024 v1.02.json` 世界书
> 核心问题: 如何将一套复杂的TRPG规则还原为可被AI驱动的自动化界面？

---

## 一、核心设计问题

当你面对 D&D 规则书时，你看到的是几百页的文本。但当你想要"自动化"它时，你实际上在问一个更根本的问题：

**"规则书里的信息，分别属于哪些不同的'信息类型'？每种类型应该用什么方式编码？"**

这套系统的设计者做了如下分类：

| D&D规则中的信息 | 信息类型 | 编码方式 | 为什么 |
|----------------|---------|---------|--------|
| 属性值、HP、法术位 | **数值状态** | 变量树 (path=value) | 频繁变化，需要精确追踪 |
| "升级时HP增加" | **变化规则** | check条件 (自然语言) | 规则复杂，AI理解比代码实现更灵活 |
| "+1 AC" | **机械效果** | EffectTag预设键 | 高频重复，压缩token |
| 车卡步骤顺序 | **流程控制** | 状态机 (Step 1→5) | 有严格的先后依赖 |
| 掷骰动作 | **随机性** | 系统层预生成宏 | 随机 vs 智能必须分离 |
| 检定结果展示 | **结构化输出** | 正则解析文本块 | AI输出文本，前端渲染UI |
| "不能施放未准备法术" | **约束规则** | constant提示条目 | 始终激活的行为边界 |

**核心洞察**：不是"写一个程序来跑D&D"，而是"把D&D规则信息按类型拆解，每种类型用最合适的载体承载"。

---

## 二、五大设计决策（逐条拆解）

### 决策1：状态用变量树，不用自然语言

**问题**：如何让AI"记住"角色的HP是32而不是30？

**错误思路**：让AI在对话中自己记。"你的角色还有32点生命值"——AI会在3轮后忘记。

**正确思路**：变量是结构化数据，不依赖AI记忆。

```
角色列表/艾尔玛/生命值/当前: 32
```

设计者的做法：
- 用一个路径树作为"source of truth"
- 每轮对话结束时，AI输出JSON Patch更新这个树
- 下轮对话开始时，宏 `{{get_message_variable::stat_data}}` 把整棵树注入prompt
- AI看到的始终是最新的状态，不需要"记住"

**为什么用JSON Patch而不是全量更新？**

全量更新每轮发送整个角色卡（~2000 tokens）。JSON Patch只发送变化：
```json
{ "op": "delta", "path": "/角色列表/艾尔玛/生命值/当前", "value": -8 }
```
20个字符解决一个问题。这是 **增量更新 vs 全量快照** 的经典取舍。

### 决策2：规则用check条件，不用代码

**问题**：D&D规则极其复杂。"短休恢复生命骰、长休恢复全部HP和一半生命骰"——如何编码？

**错误思路**：写一个规则引擎，穷举所有情况。

**正确思路**：把规则写成自然语言的check条件，让AI自己判断。

```
生命值:
  check:
    - 受到伤害时减少当前值
    - 接受治疗时增加当前值，不可超过最大值
    - 短休时可消耗生命骰恢复生命
    - 长休时恢复一半总数的生命骰和全部生命值
```

设计者的判断：**规则的解释和执行应该由AI完成，规则的"触发时机"和"更新目标"才需要结构化**。

这不是偷懒——这是正确利用LLM的优势。LLM擅长理解自然语言规则并根据上下文判断；LLM不擅长精确记忆数值状态。所以：
- 数值状态 → 结构化数据（变量树）
- 规则逻辑 → 自然语言描述（check条件）
- 各司其职。

### 决策3：流程用状态机，不用自由对话

**问题**：车卡有很多步骤（选世界→选模组→创角色→配装备→开始）。如果让AI自由对话，它会跳过步骤或一步输出全部。

**设计者的解法**：把车卡变成**严格的状态机**。

```
Step 1: Welcome → [等用户输入] → Step 2
Step 2: World Selection → [等用户选择] → Step 3 或 Step 5
Step 3.1 → [确认] → 3.2 → [确认] → 3.3 → [确认] → Step 4 或 5
Step 4: Party Building → [循环直到用户说Ready] → Step 5
Step 5: Game Launch → 输出开场叙事 → 退出状态机
```

关键设计约束：
```
[CRITICAL RULE: OUTPUT LIMIT]
1. Output ONLY ONE logic step per response.
2. WAIT for user input after every question.
3. NEVER output the entire sequence at once.
```

**为什么这很重要？** 因为LLM的自然倾向是"一次性给出完整回答"。车卡需要交互式逐步确认——你必须用非常强硬的指令打破LLM的这个倾向。

**状态机的生命周期管理**：
- `depth=0`：只在最新一轮对话中扫描（不会因为历史对话中的"Step 2"而误触发）
- `excludeRecursion=true`：不会被其他条目递归激活
- 开局结束后手动关闭：`disable=true`

### 决策4：格式化输出用"文本即协议"，不用JSON API

**问题**：AI需要输出检定结果，前端需要渲染成卡片。怎么通信？

**传统思路**：让AI输出JSON，前端解析。问题是AI经常输出不合法的JSON（缺少引号、多了逗号）。

**这套系统的做法**：定义一个极其简单的文本格式，用正则解析。

```
<dice>
发动技能: 力量检定
目标: 石门
情境: 你试图推开沉重的石门
检定细节: d20(15) + 3 (STR) = 18 vs DC 15
判定结果: 成功（Success）
结果描述: 你用尽全力，石门缓缓打开
</dice>
```

前端只需要：
```javascript
const diceRegex = /<dice>\s*(.+?)\s*<\/dice>/gs;
const fieldRegex = /^(.+?):\s*(.+)$/m;
```

**为什么这是天才设计？**

1. **AI擅长输出文本，不擅长输出合法JSON**。这个格式对人类和AI都友好——AI几乎不会出错。
2. **容错性极强**。多一行、少一行、顺序不对——都不影响解析（最多某个字段为空）。
3. **可读性**。开发者在AI输出中可以直接读懂，不需要格式化工具。
4. **自文档化**。格式本身就是文档——看到 `发动技能: xxx` 就知道这一行是什么。

**这本质上是把"正则"当成了AI和前端之间的契约语言**。正则表达式就是这个API的schema定义。

### 决策5：效果系统用压缩编码

**问题**：D&D中有大量重复的机械效果。"AC+1"、"豁免+1"、"攻击+1"——这些效果在不同物品、专长、法术中反复出现。

**设计者的解法**：建立EffectTag预设词典。

```
ac_plus_1 → AC获得+1加值
save_plus_1 → 所有豁免获得+1加值
weapon_damage_d4 → 武器伤害额外+1d4
hp_plus_5 → 最大HP+5
```

效果：
```
// 不用EffectTag（冗长）
effects: [
  { target: "ac.bonus", mode: "add", value: 1 },
  { target: "save.all", mode: "add", value: 1 }
]

// 用EffectTag（简洁）
effectTags: ["ac_plus_1", "save_plus_1"]
```

**这是信息论中的压缩编码**：高频模式用短码，低频模式用完整表示。效果：
- Token消耗从 ~60 → ~10
- AI不容易写错（不需要记住target/mode/value的精确格式）
- 新效果可以随时添加

如果预设覆盖不到（如"先攻+PB"），就用原始effects格式——**压缩和表达力不互斥**。

## 三、架构设计的三个"为什么"

### 为什么用 constant=true 而不是触发词？

观察：27个条目中，20个是 `constant=true`（始终激活），只有升级规则和快捷命令用触发词。

**原因**：这不是传统的"知识库检索"场景。D&D规则不是"查资料"——它们是**持续生效的约束**。

| 触发词模式 | constant模式 |
|-----------|-------------|
| 用户说了某个词→注入相关规则 | 无论用户说什么→规则始终在prompt中 |
| 适合：百科全书式知识检索 | 适合：行为约束/格式要求/状态注入 |
| 例："龙" → 注入龙的设定 | 例：每轮都必须有骰子序列+检定格式+更新规则 |

**设计者的判断**：规则系统的核心是约束AI行为，不是提供参考资料。约束必须始终在场。

### 为什么用 position 分层？

条目不只是"注入prompt"，而是注入prompt的**特定位置**：

| position | 含义 | 放的条目类型 |
|----------|------|------------|
| 0 (before_char) | 角色定义之前 | 行为约束 + 全局规则 (DM协议, 检定格式) |
| 4 (atDepth) | 对话历史之后 | 状态数据 + 格式模板 (骰子序列, 变量树, 更新规则) |

**为什么这样分？**

- **before_char的内容是"元规则"**：告诉AI"你是什么角色，你应该怎么行为"。放在角色定义之前=优先级最高。
- **atDepth的内容是"运行时数据"**：骰子、HP、技能。放在对话之后=AI先看到上下文，再看到当前状态，最后推理。

这不是随意放置——这是在利用LLM的**位置注意力偏差**（prompt开头和结尾的内容受到的注意力权重更高）。

### 为什么要 order 值？

```
变量输出格式: order=0 (最先)
骰子序列: order=1
更新规则: order=3
GM定位: order=5
DM要求: order=100
显示数据: order=400
检定UI: order=800
```

在同一个position内，order决定了注入顺序。设计逻辑：
- **低order → 基础设施**（变量格式、骰子——AI需要先理解"怎么用"）
- **中order → 行为规则**（GM定位、DM协议——"怎么做"）
- **高order → 输出格式**（检定UI、美化——"输出什么"）

## 四、从这套系统提炼的通用方法论

如果你想为任何TRPG规则系统（不限于D&D）设计自动化界面，可以遵循这个流程：

### 第一步：信息分类

把规则书中的所有信息按照"变化频率×编码难度"矩阵分类：

```
            变化频繁              变化稀少
          ┌─────────────┬─────────────┐
易编码    │  HP,法术位   │  种族,职业    │
          │  → 变量树    │  → 变量树     │
          ├─────────────┼─────────────┤
难编码    │  战斗中的     │  世界观设定   │
          │  战术决策     │  角色性格     │
          │  → AI推理    │  → 自然语言   │
          └─────────────┴─────────────┘
```

- 变化频繁+易编码 → **结构化数据**（变量树+自动更新）
- 变化频繁+难编码 → **AI推理**（让AI根据上下文决策，但约束边界）
- 变化稀少+易编码 → **结构化数据**（静态配置）
- 变化稀少+难编码 → **自然语言条目**（constant注入，AI自己理解）

### 第二步：流程拆解

把任何需要"逐步交互"的流程拆成状态机：

1. 列出所有步骤
2. 标注每个步骤的**前置条件**（上一步完成了吗？用户确认了吗？）
3. 标注每个步骤的**输出约束**（只能输出什么？）
4. 标注**异常路径**（用户想跳过怎么办？用户输入无效怎么办？）
5. 设置**生命周期**（什么时候激活？什么时候关闭？）

### 第三步：输出格式定义

对于每种需要"前端渲染"的输出，定义文本契约：

1. 选择包裹标签（`<dice>`, `<battlecheck>`, `<char_info>`）
2. 定义字段列表（6-7个字段最佳——太少信息不足，太多AI容易出错）
3. 定义字段值格式（d20(15)+3=18 vs DC15 —— 这个格式本身就是在教AI如何展示检定逻辑）
4. 定义解析正则（`/^(.+?):\s*(.+)$/m` —— 极简通用）

**关键原则**：格式要简单到AI几乎不可能出错。如果一个格式AI频繁出错，不是AI的问题——是格式设计太复杂。

### 第四步：压缩编码

识别规则中的"高频模式"，建立预设词典：

1. 扫描所有需要编码的机械效果
2. 统计出现频率
3. 为高频效果创建短键
4. 保留完整表达路径（effect数组）作为兜底

**判断标准**：如果一个效果出现了3次以上，就值得为它建一个EffectTag。

### 第五步：分层注入

按"元规则→行为规则→状态数据→输出格式"的顺序组织条目：

```
Position=0 (before_char) — 全局约束层
  ├─ DM角色定位
  ├─ 核心规则协议
  └─ 检定输出格式

Position=4 (atDepth) — 运行时数据层
  ├─ 当前状态变量树
  ├─ 骰子序列
  ├─ 更新规则
  └─ 更新格式模板
```

## 五、总结：这套系统真正创新的地方

| 创新点 | 传统做法 | 这套系统的做法 | 为什么更好 |
|--------|---------|--------------|-----------|
| 状态管理 | AI自己记忆 | 结构化变量树+增量Patch | AI的记忆不可靠 |
| 规则编码 | 写规则引擎代码 | 自然语言check条件+LLM推理 | 规则太复杂，代码跟不上扩展 |
| 流程控制 | 让AI自由发挥 | 强制状态机+OUTPUT LIMIT | LLM天然倾向"一次说完" |
| AI↔前端通信 | JSON API | 文本块+正则解析 | LLM输出JSON容易出错 |
| 效果编码 | 完整的effect对象 | EffectTag压缩键 | Token消耗降低6倍 |
| 信息注入 | 按需检索 | constant分层注入 | 规则是持续约束，不是参考资料 |
| 随机数 | AI生成 | 系统预生成+宏 | 消除AI幻觉骰值 |

**最核心的思想**：不要把LLM当成"需要你告诉它一切的程序"，也不要把LLM当成"可以替代一切的神"。**搞清楚什么事情LLM擅长（理解规则、生成叙事、判断情境），什么事情LLM不擅长（精确记忆、数学计算、遵守格式），然后把前者交给LLM，后者交给结构化系统和宏。**

这就是"还原DND规则到自动化界面"的完整设计思路。
